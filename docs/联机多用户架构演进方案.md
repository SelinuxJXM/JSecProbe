# JSecProbe 联机多用户架构演进方案

> 版本：v1.1 ｜ 日期：2026-11-20 ｜ 基于 v2.5.4 代码实证盘点
>
> 目的：为未来「多用户联机 / 联网」提前规划可落地的演进路线，降低后续动工的返工成本。
>
> **严谨性声明（v1.1 新增，务必先读）**：本文分两类内容，可信度不同，不要混为一谈——
> - **【已核实】**：现状数字与代码事实，经逐项 grep / 读码复核，可信。
> - **【估算】**：工作量（人·月）、阶段划分、冲突策略、数据库选型等，是基于现状的**工程判断**，不是实测。尤其人·月是量级估算（误差可达 ±50%），未做 WBS 逐任务拆解，**不可直接作为排期承诺**，动工前必须按第九节的方式细化。
>
> v1.1 勘误与补强（相对 v1.0）：修正 handler 数口径、修正"Drizzle 事务可平移"的错误判断、解决"阶段0 加字段 vs 服务端全量重建"的冲突、补充工作量估算方法、补充 4 个原方案未覆盖的关键维度（见第九节）。

## 一、结论先行

**推荐路线：保留 Electron 富客户端，走「本地优先（Local-first）+ 中心服务端 + 增量同步」，而不是纯 Web 重写。**

三条核心判断：

1. **现场测评必须离线可用**。当前 90% 功能（项目、资产、测评记录、问题、截图、采集、报告、认证）纯本地运行，现场常无网。纯 Web 方案会直接丧失这个能力，且离线同步复杂度最高。
2. **270 个 IPC 通道重写成 REST 是巨大浪费**（保守 6–10 人·月，【估算】）。本地优先方案可在几乎不动前端和 IPC 契约的前提下加一个同步层，工作量低一个数量级。
   - 【已核实】通道口径：`electron/ipc/` 下 23 个文件共 **265** 个 `ipcMain.handle`，加 `update.service.ts` 的 **5** 个 = **270**。（v1.0 文中一处写"266"为口径错误，已更正。）
3. **本地 AI 引擎与采集连接器无法上云**。Ollama/Herdsman 是用户本机进程，SSH/WinRM/MySQL/Oracle 等连接器需要客户端直连被测系统——这些决定了客户端形态必须保留。

**数据库选型：推荐 PostgreSQL**（理由见第六节，【估算】）。**ORM 继续用 Drizzle**：业务层查询调用可平移，但**事务层不能简单平移**（见 2.1 勘误，这是 v1.0 的重大遗漏）。

**总工作量量级（单开发者，【估算】）**：本地优先路线约 **6–9 人·月**；纯 Web 重写约 12–18 人·月且风险高。**建议本地优先。** 这两个数字的推算方法见第九节，**误差可达 ±50%，不可直接当排期**。

## 二、当前架构盘点（迁移约束）

### 2.1 数据层（工作量：中高）

| 指标 | 数值 | 迁移含义 |
|---|---|---|
| 表数量 | 28 张 | 全量建表需重写为 PG 方言 |
| 主键类型 | 27 张 TEXT(UUID) + 1 张 prompt_key | **利好**：JS 侧 `randomUUID()` 生成，与数据库无关，ID 逻辑不用改 |
| 外键约束 | 0 个 | 级联删除靠手工枚举，PG 侧需重建引用完整性策略 |
| Drizzle 查询构建器调用 | 542 + 1029 处 | **可平移**，换驱动即可，不用重写 |
| Drizzle `sql\`` 模板 | 45 处 | 大部分可移植，少数需审（LIKE ESCAPE 等） |
| Drizzle 事务 `db.transaction` | 28 处 | **⚠️ v1.0 判断错误**：其中 **14 个事务块内含 `await`**（【已核实】）。better-sqlite3 下事务是同步的，包住 await 使事务边界名存实亡；迁到 PG 后必须重构成显式 `BEGIN/COMMIT` + 把 tx 透传进所有函数，**这是实打实的返工，不是平移** |
| better-sqlite3 原生调用 | **86 处**（prepare 51 / exec 40 / pragma 7 / transaction 2） | **同步改异步**，工作量最集中 |
| `PRAGMA` | 22 处 | PG 无等价物，需改用 `information_schema` / 删除 |
| `strftime` 默认值 | 6 处 | 改 `NOW()` / `CURRENT_TIMESTAMP` |
| `sqlite_master` 查询 | 5 处 | 改 `pg_catalog` / `information_schema` |
| `VACUUM INTO` | 1 处 | 改为服务端备份策略 |
| 12 个 SQLite 迁移 SQL + `autoCreateTables()` | 纯 SQLite 方言 | **不可复用**，PG 侧建议 drizzle-kit 全量重新生成 |

**多租户隔离现状**：
- `project_id` 覆盖 22 张表（业务数据天然挂在项目下）——**核心隔离维度已具备**。
- 但有 **12 张全局共享表无 project_id / tenant 字段**：`users`、`standards`、`assessment_items`、`knowledge_*`、`ai_configs`、`ai_prompts`、`ai_cloud_models`、`external_links`、`major_risk_catalog`、`system_settings`、`report_templates`、`assessment_checkpoints`。多租户时需加 `tenant_id`。

**附件存储**：6 个 DB 列存本地相对路径（`ai_messages.attachments`、`projects.topology_attachments`、`assessment_records.screenshot_paths`、`issues.evidence_files`、`knowledge_documents.file_path`、`collection_documents.file_path`），物理落在 `appData/ai-chat-attachments`。迁移到对象存储需新增文件服务层桥接。

### 2.2 认证与权限（工作量：低-高，视是否做细粒度）

**已有基础（利好）**：
- `users` 表存在，非硬编码；bcryptjs cost=12；`admin/admin123` 种子用户。
- 会话：内存 Map + `session.json` 磁盘持久化（safeStorage 加密 token），24h 超时，10min 节流写盘。
- 角色：`admin` / `assessor` 两角色（users.role 文本列）。
- 审计表 `operation_logs` 字段完整（user_id / username / ip_address / action / module / target / detail_json）。

**关键缺口**：
| 缺口 | 严重度 | 说明 |
|---|---|---|
| 单会话单例 | 高 | `AuthService.activeToken` 单例，同一进程只能有一个活动会话；`activeToken` 需改为 Map |
| 无数据级权限隔离 | **高** | **0 个 handler** 做「用户A不能看用户B项目」校验；`project:list` 返回全部项目 |
| `project_members` 表形同虚设 | 高 | 表已建好（含 project_id/user_id/role/assigned_domains），但鉴权链路**零引用** |
| 无 RBAC 模型 | 中 | 无 roles / permissions 表，角色仅文本列 |
| 审计覆盖不足 | 中 | 约 50%+ 业务写操作未写 operation_logs |
| 前端路由守卫只查 token | 中 | 不区分角色与项目权限 |

**统计**：266 个 handler 中，210 走 wrap 包装（79%），12 个显式 `requireRole`，**0 个数据级权限校验**。约 80+ 个按 projectId 查询的 handler 需加项目成员过滤。

### 2.3 架构边界（工作量：高，但本地优先路线可绕开）

| 指标 | 数值 |

| `ipcMain.handle` 通道 | **270 个**（含 update 5 个） |

## 三、演进路线对比

| 路线 | 做法 | 工作量 | 风险 | 离线能力 | 结论 |
|---|---|---|---|---|---|
| **A. 本地优先富客户端（推荐）** | 保留 Electron + IPC，加 SyncService 增量同步 + 服务端 | 6–9 人·月 | 低 | ✅ 完整保留 | **推荐** |
| B. 渐进式 Web 化 | 逐步把 IPC 换成 HTTP，前端迁移 Web | 8–12 人·月 | 中 | ⚠️ 需重建 | 中长期备选 |
| C. 纯 Web 重写 | 抛弃 Electron，Vue + IndexedDB + WebSocket | 12–18 人·月 | 高 | ❌ 丧失 | 不推荐 |

路线 A 的核心：**前端和 270 个 IPC 契约基本不动**，在 handler 之下插入同步层。AI 密钥上收到服务端 AI 网关，本地引擎保留本地直连。

## 四、分阶段实施路线（可直接排期动工）

### 阶段 0：地基准备（可在现有代码上无感进行，低风险）
目标：先把"未来一定需要、现在做不痛"的事做掉，避免以后返工。

- [ ] 给 12 张全局共享表预留 `tenant_id` 字段（default 值，暂不参与逻辑）。
  - **v1.1 修正**：此步与阶段 1「服务端全量重建」存在衔接问题——本地 SQLite 加的字段不会自动出现在新 PG 库。正确做法：**只改 `schema.ts` 定义（单一事实源）并让本地迁移跟上**，阶段 1 的 PG 库由同一份 schema 用 `drizzle-kit generate --dialect pg` 重新生成，从而天然包含 `tenant_id`。**务必维护好"一份 schema、两套迁移产物"的映射关系**，见第九节风险 R-新1。
- [ ] `AuthService.activeToken` 单例 → `Map<userId, token>`；`requireSession` 改为按传入 token 校验，不再回退进程级单例。
  - 【已核实】当前确实是 `let activeToken: string | null = null`（auth.service.ts:27）单例设计。
- [ ] 所有按 `projectId` 查询的 handler，统一加一个 `assertProjectAccess(userId, projectId)` 守卫骨架（先做成"全放行"，集中改造后再收紧）。
- [ ] 补全审计：project / asset / issue / assessment / risk 写操作统一走 `writeOperationLog`，并传 `ipAddress`。
- [ ] 附件路径统一为「相对路径 + 逻辑 file_id」，为对象存储抽象出 `FileStore` 接口（本地实现先落地）。
- [ ] 引入领域事件/操作日志表（可作为同步单元，复用 `operation_logs` 或新建 `sync_outbox`）。

**产出**：架构"可插拔点"就位，后续阶段无需大改业务代码。预计 1–1.5 人·月。

### 阶段 1：服务端骨架 + 认证上收（中）
目标：跑起一个中心服务端，用户从"本地登录"变成"服务端登录"。

- [ ] 新建 `server/` 包：Node + Fastify/Nest + Drizzle(pg) + PostgreSQL。
- [ ] `schema.ts` 方言改造（`text`→`text/uuid`、`integer`→`integer`、`strftime`→`NOW()`），`drizzle-kit generate` 生成 PG 迁移；全量重建，不沿用 12 个 SQLite 迁移。
- [ ] 服务端实现 `/api/auth/login|refresh|logout`，JWT（access + refresh），bcrypt 复用。
- [ ] 服务端 RBAC：roles / permissions / role_permissions 表；`project_members` 真正参与鉴权。
- [ ] 客户端 `auth.service.ts` 改为服务端认证，本地 token 缓存 + 刷新。
- [ ] 数据隔离：80+ handler 加 `project_members` JOIN 过滤，收紧为"只看自己被授权的项目"。

**产出**：多用户可登录、各自只看自己的项目。预计 2–2.5 人·月。

### 阶段 2：同步引擎（核心，中高）
目标：本地 SQLite ↔ 服务端 PG 增量同步，保留离线能力。

- [ ] 服务端为 22 张业务表提供增量拉取/推送端点（按 `updated_at` 游标 + 软删除 tombstone）。
- [ ] 客户端 `SyncService`：本地写操作进 outbox，联网时批量推送；服务端变更按游标下拉。
- [ ] 冲突策略：**测评记录/问题等关键数据用"字段级 last-write-wins + 冲突留痕"**；纯追加表（日志、AI 对话）用去重合并。
- [ ] 同步状态 UI（未同步条数、最后同步时间、冲突列表）。
- [ ] 断点续传、限流、失败重试。

**产出**：现场离线采集，联网后自动同步。预计 2–2.5 人·月。（这是全案技术含量最高的一环，建议单独评审。）

### 阶段 3：AI 网关与密钥上收（中）
目标：AI 密钥不再散落客户端。

- [ ] 服务端 AI 网关：`/api/ai/chat|analyze|batch`，多模型路由、限流、计费、密钥托管。
- [ ] 客户端 `ai.ipc.ts` 约 24 处调用改为走服务端网关（保留本地 Ollama/Herdsman 直连分支）。
- [ ] 代理配置由服务端统一下发。

**产出**：密钥集中、用量可管。预计 1–1.5 人·月。

### 阶段 4：附件对象存储 + 服务端备份（中）
- [ ] 引入 S3 兼容对象存储（MinIO 自建 / 云 OSS），`FileStore` 切换到远端实现。
- [ ] 附件上传/预览/下载改走文件服务；离线先落本地队列，联网补传。
- [ ] 备份从"本地 ZIP"改为"服务端快照 + 定期归档"。

预计 1–1.5 人·月。

### 阶段 5（可选）：渐进式 Web 化
当客户端-服务端稳定后，若确需浏览器访问，再按模块把 IPC 替换为 REST + WebSocket。可只 Web 化"管理/报告/统计"类只读场景，现场采集仍保留 Electron 客户端。

## 五、关键技术决策细化

### 5.1 多租户隔离模型
- 采用 **tenant（单位/组织）+ project（系统）+ project_members（成员授权）** 三级。
- 业务表按 `project_id` 隔离（已具备）；全局表加 `tenant_id`。
- 所有列表接口强制带 `JOIN project_members WHERE user_id = 当前用户`，作为中间件统一注入，避免逐个 handler 漏写。
- 超级管理员（admin）可跨租户，但操作写审计。

### 5.2 离线同步与冲突
- 采用 **outbox + 增量游标** 模式，不用 CRDT（过重，且测评数据结构化、冲突面小）。
- 每张可编辑表加 `version` / `updated_at`；客户端离线写本地并记 outbox。
- 服务端按 `updated_at > cursor` 返回增量；客户端合并。
- 冲突：同一记录双方都改 → 保留服务端版本 + 本地版本进 `conflicts` 表，UI 提示人工选择。
- 附件单独走文件服务，附件记录与业务记录用 file_id 关联，避免大对象进同步流。

### 5.3 数据库选型：PostgreSQL vs MySQL
推荐 **PostgreSQL**，理由：
- 本项目大量 JSON 以 TEXT 存储（拓扑附件、证据文件、AI 消息、测评点），PG 的 `JSONB` 可直接升级，查询/索引更强。
- 主键是 UUID 字符串，PG 有原生 `uuid` 类型。
- `RETURNING`、`ON CONFLICT`、部分索引、全文检索对报表/检索场景更友好。
- Drizzle 对 PG 的支持最成熟。
- 若团队更熟悉 MySQL 或运维已有 MySQL 体系，MySQL 8 亦可，工作量差异不大（主要差在 JSON 与 UUID 处理）。

### 5.4 迁移策略
- **服务端从零建库**：用 drizzle-kit 基于改造后的 schema 生成全新 PG 迁移，不沿用 12 个 SQLite 迁移文件与 `autoCreateTables()`（两者已是两份独立 DDL，存在漂移）。
- **存量数据迁移**：写一个一次性 ETL 脚本，读本地 SQLite → 映射到新库（UUID 保持不变，外键按 project_id 重建）。先迁一个真实项目验证，再批量。
- **双跑验证期**：新库上线前，客户端同时写本地与服务端，比对一致性后再切流。

## 六、风险清单

| 风险 | 等级 | 规避 |
|---|---|---|
| 离线同步冲突 | 高 | outbox + 版本游标 + 冲突留痕 + 人工裁决，Phase 2 单独评审 |

## 七、给"现在就能做"的建议

不需要等立项，以下改动**当前做零风险、未来必受益**：

1. 全局表补 `tenant_id` 占位字段（含迁移与 schema，走现有 0012 迁移）。
2. `AuthService` 单例会话改 Map（本地行为不变，未来支持多会话）。
3. 抽出 `assertProjectAccess()` 守卫并接到关键 handler（先全放行，未来收紧一行改）。
4. 补 `operation_logs` 写入覆盖 + `ipAddress`。
5. 抽出 `FileStore` 接口 + 本地实现，把附件读写统一收口。
6. 为 28 张表补 `updated_at` / `version` 字段（同步游标所需，缺失的 7 张表优先）。

做完这 6 项，后续任何路线都能平滑接入，且当前单机版本行为完全不变。

## 九、严谨性自评与方案盲区（v1.1 新增，请务必读）

这一节是主动交代"本方案哪里不够硬"，供你判断是否需要在动工前补调研。诚实比好看重要。

### 9.1 已核实 vs 未核实

**【已核实】——可直接采信：**
- 表数 28、handler 数 265+5=270、preload 方法 32、事件 14、`project_id` 覆盖 22 处、`tenant` 字段 0 处（schema.ts 中确实无 tenant）、`deleted_at` 0 处、`activeToken` 单例、事务块含 await 有 14 个。
- 这些是我逐项 grep / 读码核对过的。

**【估算】——不能当结论：**
- 所有"人·月"数字、阶段顺序、工作量分级（低/中/高）、数据库选型、冲突策略。**这些是工程判断，未经可行性验证、未经 WBS 拆解。**
- 尤其"6–9 人·月"是怎么来的？坦白说：是基于"270 通道 + 86 处原生 SQL + 同步引擎复杂度"的直觉量级，**没有逐任务估算，误差可达 ±50%**。v1.0 把它写得太像结论了，这是不严谨的。

### 9.2 v1.0 的三个实质错误（v1.1 已修）

1. **handler 数口径不一致**：文中同时出现 266 与 270。正确是 265（ipc/）+ 5（update.service.ts）= 270。
2. **"Drizzle 事务可平移"是错的**：14 个事务块内含 `await`，迁移 PG 必须重构事务边界。已修正。
3. **阶段 0 与全量重建的衔接冲突**：已修正为"一份 schema 定义、两套迁移产物"。

### 9.3 本方案仍未覆盖 / 覆盖不足的维度（重要）

以下不是我漏想的细节，而是**会影响架构选型的实质问题**，动工前建议补调研：

1. **并发写SameRecord的真实冲突模型未定**。
   方案只说"字段级 LWW + 冲突留痕"，但没有回答：两个测评师同时编辑同一条测评记录的不同字段怎么办？同一字段怎么办？这是本地优先架构最核心的难点，直接决定数据是否会丢。**当前只是给了个方向，没给出可验证的算法。** 建议动工前先做一个"双客户端同时编辑"的 PoC 验证冲突策略。

2. **同步单元粒度未定义**。
   按行同步？按项目同步？按操作日志同步？方案倾向于"operation_logs/outbox 作增量单元"，但没论证：一条测评记录有 20+ 字段，用户改了备注，同步整行还是同步字段差量？这影响带宽、冲突概率和实现复杂度。**未定。**

3. **数据迁移的实操风险被低估**。
   "写个 ETL 脚本把 SQLite 数据搬到 PG"——这句话太轻巧。28 张表、UUID 主键、JSON 字段、附件相对路径、存量 3.5MB 数据（含 2660 条测评记录），字段映射、外键重建、附件路径迁移、校验对账、回滚方案，**每一项都是工作量**。方案里只用了一段话带过。

4. **未验证的核心假设：Drizzle 跨方言是否真的"业务层不用改"**。
   方案说"542+1029 处查询调用可平移"，但没有做任何 PoC。风险点：`sql\`` 模板里可能有 SQLite 特有函数、`.get()/.all()` 同步返回在 PG 下要改 await、LIKE/ESCAPE 行为差异、布尔值 0/1 vs true/false 映射、日期字符串格式。**这些只有在真实切换后才能全暴露。** 建议在阶段 1 之前先做一个"单表 CRUD 跨方言"的 spike。

5. **服务端部署形态与合规未讨论**。
   联机意味着测评数据集中存储——涉及被测单位的拓扑、漏洞、凭据，这是敏感数据。放在哪里？客户内网自建？公有云？等保/保密合规怎么满足？**这决定服务端架构（是否要支持私有化部署、数据加密、访问审计），方案完全没提。** 如果该问题答案是"必须客户内网私有化"，那"中心服务端"的形态和 SaaS 完全不同。

6. **成本模型空白**。
   服务端机器、数据库、对象存储、AI 网关转发的 token 成本——多用户下谁付费、怎么限额、怎么防止滥用，方案只字未提。

7. **AI 网关的"本地引擎保留"与"云端密钥上收"之间的边界没划清**。
   用户离线时用本地 Ollama 分析了内容，联网后这部分数据要不要同步、用什么标识区分本地 AI 与云端 AI 的产物，未定义。

### 9.4 因此，这个方案的正确用法

**它是一张"地图"，不是"施工图"。** 它可以帮你：
- 判断路线方向（本地优先 vs 纯 Web）——这个判断我比较有信心；
- 知道有哪些硬骨头（数据隔离、同步冲突、原生 SQL、事务重构）——这些是真实盘点出来的；
- 知道从哪几件事开始（阶段 0）——这些方向是对的。

它**不能**直接用来：
- 做排期承诺（人·月是拍的）；
- 做技术选型的最终决策（PG vs MySQL 没做 spike）；
- 跳过 PoC 直接进入大规模开发（核心假设未验证）。

**动工前建议的最小验证清单（按顺序）：**
1. schema 单表切 PG 的 CRUD spike（验证 9.3-4）；
2. 双客户端同时编辑同一条记录的冲突 PoC（验证 9.3-1）；
3. 明确服务端部署形态与数据合规边界（验证 9.3-5）；
4. 用 WBS 把阶段 0 拆到"任务-人天"，重新估算总量（修正 9.1）。

### 9.5 一句话回答"够不够严谨全面"

**现状盘点部分：够严谨**（数字都复核过）。
**未来方案部分：方向可信，细节不够严谨**——有几个实质错误（已修）、有 7 个影响选型的未覆盖维度（已列）、工作量是量级直觉而非估算。**作为"提前思考、方便动工"的起点够用；作为"可以直接开工的施工图"不够，需要按 9.4 补验证。**
